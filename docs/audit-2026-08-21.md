# Repository audit — 2026-08-21

Record of why the previous repository contents were removed.

The scaffold is **not lost**. It remains permanently in git history at tag
`scaffold-archive` (commit `31ebc64`). The reset was an ordinary commit on top,
not a history rewrite, so anything here can be recovered with:

```bash
git show scaffold-archive:Nadir/sim/env.py     # single file
git checkout scaffold-archive -- Nadir/        # whole tree, into working dir
```

## What the scaffold actually was

`models/nadir.xml` was **Gymnasium's `walker2d.xml`**, rescaled and recoloured.
The fingerprints are unambiguous: the `rootx`/`rootz`/`rooty` planar floating
base, `thigh_joint`/`leg_joint`/`foot_joint` naming, `<body name="torso" pos="0 0 1.25">`,
`gear="100"`, the stock checker-plane skybox.

Everything else was built around that: a Gymnasium env, Stable-Baselines3 PPO,
and an ESP32 firmware target.

Provenance evidence:

| Evidence | Meaning |
| :--- | :--- |
| Three files fall back to `"../walker/ppo_bipedal_walker.zip"` | The real origin — a sibling directory named `walker` |
| `checkpoints/` metadata: Windows 11, SB3 2.9.0, `n_envs=20`, `policy_kwargs={}` | Trained on another machine with **default 64×64 layers** |
| `train.py` specifies **256×256** | The shipped checkpoint therefore could not have come from this repo's trainer |
| Exported weights are `17→64→64→6` | A stock Walker2d-v5 PPO agent |
| History was `firstcommit` (an ESP32 soil-moisture script) then `Add files via upload` | Assembled through the GitHub web UI, no development history |

## Why it could not be adapted

### The robot was wrong

| | Scaffold | Nadir |
| :--- | :--- | :--- |
| Height | 1.25 m | 0.30–0.40 m |
| Mass | 11.4 kg | ~1.5 kg |
| DoF | 6, **planar** (pitch only) | 12–14, full 3D |
| Compute target | ESP32-S3 + PCA9685 PWM | Raspberry Pi + serial bus servos |

### The control paradigm was wrong — the decisive issue

`models/nadir.xml` used `<motor>` actuators: MuJoCo's **direct-torque**
actuator. There was no `<position>` actuator and no PD loop anywhere.

| | Scaffold | Nadir |
| :--- | :--- | :--- |
| Control mode | Direct joint torque | **Position target** (STS3215 internal PD) |
| Peak hip torque | `gear="100"` → **100 N·m** | STS3215 ≈ **3 N·m** |
| Actuator model | Ideal, instantaneous, no backlash | ~0.87° backlash, real lag, bus latency |

The simulated actuator was roughly **33× stronger** than our servo and answered
a fundamentally different question. A policy trained there learns *how much
torque to apply* — not a command our hardware accepts. Every reward weight,
termination threshold and hyperparameter was tuned around that.

The documentation hedged this rather than stating it: both `rl_formulation.md`
and `env.py` said "torques **/** target angles". That slash obscured the single
most important decision in the project. The XML settled it: torque.

### The training stack was wrong

Stable-Baselines3 + PyTorch + `SubprocVecEnv` — CPU multiprocessing, one
process per environment, scaled by `os.cpu_count()`. Zero occurrences of `jax`,
`mjx`, or `playground`.

That is the wrong axis of parallelism for a GPU cluster. MJX gives thousands of
parallel environments on one GPU; `SubprocVecEnv` gives ~20 on a workstation.
Porting is not a config change — MJX needs a JAX-native functional environment
and a different training entry point. None of `sim/env.py` survives it.

### The firmware had never been run

Two proofs:

**The observation vector was 15/17 constant zeros.** `main_esp32.py` initialised
`joint_angles = [0.0] * 6` and `joint_vels = [0.0] * 6`, fed them to the policy,
and **never assigned to them again**. Torso height and both velocities were
hardcoded `0.0`. Only pitch and pitch-rate carried real data.

This was structural, not a typo: PCA9685-driven PWM servos have **no position
feedback**. Nothing in that BOM could ever have filled those twelve slots. The
design could not close the loop. (Our STS3215s report position, load, current
and temperature over the bus — which is precisely why the servo choice matters.)

**Inference could not make rate.** The exporter emitted a pure-Python MLP —
nested loops, `sum(r * xi for ...)`. At 17→64→64→6 that is 5,568
multiply-accumulates per step, **278k/second at 50 Hz**, interpreted, on an
ESP32. Off by more than an order of magnitude.

The foot-contact switches were read into variables that were never used.

### No command conditioning

The 17-dim observation had no velocity command, no heading input, no gait phase
signal and no previous-action term. The reward was simply "go forward fast".

The policy could not be steered — it had exactly one behaviour. A modern bipedal
locomotion approach (command-conditioned, reference-motion-guided, with `last_action`
in the observation) requires a different observation design from the ground up.

## Documentation that described things that did not exist

This is why deletion was preferred over incremental repair.

- `docs/sim_to_real.md`, under the heading **"Strategies Implemented in Nadir"**,
  specified domain randomisation (±15% mass, friction ∈ [0.6, 1.4]), a 1–2 step
  latency queue, and action low-pass filtering with β ∈ [0.4, 0.7].
  **None of the three existed.** `grep -i domain_random` → 0 hits. The only
  stochasticity was ±0.015 reset noise.
- `README.md` documented `.github/workflows/ci.yml` ("Automated CI test suite")
  and `.gitignore`. Neither file existed.
- `README.md` promised a `nadir_weights.h` C export. No such function existed.
- `training/config.yaml` was never read by anything; `pyyaml` was declared in
  both manifests and never imported. Every value was separately hardcoded in
  `train.py` — and had already drifted (YAML said 256×256, checkpoint was 64×64).
- Declared but never imported: `pyyaml`, `tensorboard`, `matplotlib`, `tqdm`,
  `onnx`, `onnxruntime`.
- `__pycache__` was committed, including a 166 KB `.pyc`.
- `env.py` carried `BipedalWalkerEnv = NadirBipedalWalkerEnv` commented
  "Alias for backwards compatibility" — in what was the first commit.
- `pytest` was a declared dev dependency. There were no tests.

The danger was not that the scaffold was incomplete. It was that it looked
finished — badges, a mermaid architecture diagram, LaTeX-typeset MDP formalism,
a roadmap with six items ticked, and a "pretrained" checkpoint that loads and
walks in the viewer. Someone reading `sim_to_real.md` in six months would
believe the domain-randomisation ranges were configured and lose a week
debugging a sim-to-real gap with an unrelated cause.

## What was kept

1. `LICENSE` (MIT).
2. The number **50 Hz**.

That is the complete list.

## What was notably absent — good news

No ROS, no ROS 2, no Isaac Lab, no Isaac Gym, no Gazebo, no vision or
perception code wired into the control loop. The two heaviest failure modes did
not occur, so nothing had to be untangled.
