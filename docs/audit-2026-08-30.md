# Repository audit — 2026-08-30

Record of what was wrong with the training stack merged in `f751b86`
("Add full Nadir 10-DOF MJX simulation, training, vision, and deploy stack")
and what was changed on branch `rob` to make Phase 0 actually run.

**Nothing is lost.** All of this is an ordinary branch off `main`; no history
was rewritten. Every removal can be recovered:

```bash
git checkout main -- checkpoints/          # the 169 MB of SB3 checkpoints
git diff main..rob -- Nadir/               # every code change, reviewable
```

---

## Summary

The stack that landed in `f751b86` is the *second* time this repository has
been given a professional-looking scaffold that could not work. The 2026-08-21
audit caught a Walker2d clone with torque actuators. This one gets the headline
constraint right — it does use `<position>` actuators — and then fails
underneath, in the reward sign, the termination condition, and the rollout
loop.

Two facts frame everything below:

1. **It could not start on this cluster.** `Nadir/training/train.py` imported
   `nadir.sim.env_mjx` — lowercase — while the package directory is `Nadir/`.
   There is no `pyproject.toml`, no `setup.py`, and no lowercase `nadir/`. That
   import resolves on a case-insensitive macOS filesystem and is a hard
   `ImportError` on Linux. `scripts/train.sh` compounded it: `--partition=gpu`
   (no such partition on Leonardo) and `conda activate nadir` (no such env).
2. **Had it started, it could not have learned.** The defects in §2 are not
   tuning problems. Each one independently prevents walking.

The tensorboard log committed alongside it (`events.out.tfevents...tedsomnibook`)
and the 101 Stable-Baselines3 `.zip` checkpoints are from a different, earlier
SB3 training run on a laptop — not from this MJX code, which had never
completed a single update anywhere.

## 2. Why it could not have learned

### 2.1 The upright reward paid the robot to fall over

`Nadir/sim/rewards.py`

```python
def upright_reward(projected_gravity):
    return jnp.square(projected_gravity[2] + 1.0)
```

`projected_gravity` is the world down-vector `[0, 0, -1]` expressed in the body
frame, so `pg_z == -1` when the torso is upright.

| Attitude | `pg_z` | Reward returned | Weight |
| :--- | ---: | ---: | ---: |
| Upright | −1.0 | **0.0** | +0.5 |
| Horizontal | 0.0 | 1.0 | +0.5 |
| Inverted | +1.0 | **4.0** | +0.5 |

The sign is inverted. Being upside down was worth four points; standing was
worth nothing.

### 2.2 Every environment terminated on step 1, forever

`Nadir/sim/env_mjx.py`

```python
done = jnp.where(projected_gravity[2] < 0.0, True, False)  # "torso tipped over"
```

Upright is `pg_z ≈ −1`, which is `< 0`. So `done` was `True` from the first
step of every episode, permanently. The comparison should be `> 0`.

### 2.3 Nothing ever reset a terminated environment

Neither `env.step` nor the PPO rollout in `Nadir/training/ppo.py` reset an
environment when `done` was raised. Combined with 2.2, `(1 - done) == 0` at
every step, and the GAE recursion

```python
delta = reward + gamma * next_value * (1 - done) - value
gae   = delta + gamma * gae_lambda * (1 - done) * gae
```

collapses to `advantage = reward - V(s)`. No bootstrapping, no trace, no credit
assignment across time. It was a one-step bandit wearing a PPO costume — it
could not have learned any behaviour requiring more than one step of foresight,
which is all of walking.

### 2.4 The base-height target was physically unreachable

`base_height_reward(target_height=0.32)`. Forward kinematics on the shipped
MJCF gives:

| Pose | Torso height with soles on the floor |
| :--- | ---: |
| Default pose (knee 0.5, ankle −0.3) | **0.2577 m** |
| Straight-legged (all joints zero) | **0.2700 m** |
| Reward target | **0.3200 m** |

The target was 5 cm above the robot's absolute maximum. The term's gradient
therefore pointed permanently upward — a standing incentive to jump.

Relatedly, `<body name="torso" pos="0 0 0.35">` spawned the robot 8 cm in the
air on every reset.

### 2.5 The actuator ctrlrange silently clamped the action space

Every `<position>` actuator carried `ctrlrange="-1 1"`. For a position
actuator `ctrl` is a **goal angle in radians**, so this is a joint-angle limit:

| Joint | Joint range (rad) | ctrlrange | Reachable |
| :--- | :--- | :--- | :--- |
| knee_r / knee_l | −0.1 … 2.0 | −1 … 1 | **half** |
| hip_pitch_r / _l | −1.2 … 1.2 | −1 … 1 | clipped both ends |
| ankle_pitch | −0.8 … 0.8 | −1 … 1 | ok |

MuJoCo clamps silently, so this produced no warning of any kind.

### 2.6 The velocity command was hardcoded and never resampled

`command = jnp.array([0.5, 0.0, 0.0])` was set at reset and never changed.
`command_ranges` and `command_resample_steps` in `config.py` were dead
configuration. The policy took a command as input but was only ever trained on
one value, so it was not a velocity-conditioned policy.

### 2.7 The velocity tracking reward compared frames that do not match

The reward used `base_lin_vel = new_data.qvel[:3]`, the **world-frame** base
velocity, against a body-frame command. Once the robot turned, "walk forward"
meant "walk along world +x" regardless of heading.

### 2.8 The privileged observation was 54/57 constant

The critic's 98-dim observation appended `jnp.zeros(50)` labelled
`terrain_heights` over flat ground, a constant `1.0` friction, and a constant
zero external force. Fifty-four of the fifty-seven privileged dimensions
carried no information at all.

### 2.9 Reward, latency and domain randomisation were dead code

* 3 of 12 configured reward terms were used. `RewardWeights` in `config.py`
  was never read by anything, and had drifted from the `RewardConfig` the env
  actually used.
* `sim/domain_rand.py` and `sim/terrains.py` are never imported by the env.
  `control_latency` is computed and thrown away.
* Non-negotiable #3 requires latency and DR ranges to come from measured
  `unit_variation`. `hardware/measured/actuators.yaml` is `status: unmeasured`
  and entirely `null` — correctly so. The DR ranges in `domain_rand.py`
  (`kp` ×0.8–1.2 etc.) are invented, which is exactly what that rule forbids.

### 2.10 The ONNX exporter would not have matched the trained policy

`Nadir/export/export_onnx.py` had three independent defects:

* it applied `torch.relu` between layers while the network trains with **ELU**;
* it parsed the parameter tree as `params/Dense_k/...`, but `ActorCritic`
  nests submodules as `params/actor/Dense_k/...` — so it would have mixed
  **critic** weights into the exported actor;
* it ordered layers by string sort (`Dense_10 < Dense_2`).

Its `validate_export` compared a `(mean, log_std)` tuple against a single
array and would have raised before reporting any of this.

## 4. What is honestly still missing

Stated plainly, because non-negotiable #2 and #3 are not satisfied by this
branch and should not be reported as if they were:

* **Domain randomisation is off, and latency is pinned at 0.** The delay FIFO
  and the config hook exist in `sim/env_mjx.py`, but the ranges must come from
  `hardware/measured/actuators.yaml`, which is `unmeasured` by design. Turning
  DR on with invented ranges would satisfy the letter of #3 and violate its
  point. This is blocked on Phase 1 system-ID, not on code.
* **`armature`, `damping`, `frictionloss`, `kp`, `kv` in the MJCF are
  provisional**, labelled as such in the file. They exist so the sim is
  numerically stable at dt = 2 ms. They are not system-ID output and must not
  be treated as measurements.
* **This is still a reimplementation.** CLAUDE.md defines Phase 0 as
  *"reproduce upstream's sim training on the cluster, unmodified"* and says we
  *"inherit its stack rather than reimplement it."* This branch repairs the
  custom stack; it does not make it upstream's. Getting
  `Open_Duck_Playground` running on Leonardo remains the more faithful reading
  of Phase 0, and would give this code a reference that is known to walk.
* **No hardware has been touched.** Everything here is sim.
